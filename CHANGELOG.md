# Changelog

Versions follow [semantic versioning](https://semver.org/). What counts as a compatible change is defined in the [compatibility policy](docs/compatibility.md).

## 1.4.1

A package listed more than once in one system gives one finding and one alert, and upgrading sends nothing again. Existing configurations, inventories and databases work unchanged. To be published under the default `latest` tag; the GitHub Action is used as `uses: ShieldaAI/security-watch@v1.4.1`, the image is `ghcr.io/shieldaai/security-watch:1.4.1`.

### Fixed

- **One package listed twice in one system gave two findings and two alerts.** A package release is now one component of the system, however often it is listed: an SBOM that lists it once per path with a `bom-ref` of its own (Syft does this for a package found in two folders), or a system that combines `components:`, `libraries:`, `sbom:` and `lockfile:` naming the same release. Versions written two ways count as one release, as the SBOM importer already judged them (Python `2.0` and `2.0.0`, Go `v1.9.1` and `1.9.1`); different releases stay separate. One listing is kept: the one declared under `components:` (where remediation records and verification results are written), then an SBOM entry, a `libraries:` entry, a lockfile entry. Its note lists every place the package was found (at most 500 characters, with room kept for an operator's note), it takes the others' dependency edges and remediation records, and the package URL (from a listing that writes the version the same way), reference and verification results it lacks. `security-watch check` (with `--sbom`, a project, or `--package` named twice) reports such a package once. A scan folds an inventory it is given directly as well, such as a rehearsal snapshot.
- **A finding keeps going when its listing changes.** A package release keeps the component ID it had at the previous scan when that ID is no longer used but the release is still there (the copy that was kept was removed and another stays, or the SBOM generator gave the package a new `bom-ref`), so the finding already reported goes on instead of a new alert. `vex` and `shield-candidates` use the same IDs.
- **Upgrading sends nothing again.** At the first scan after the upgrade, the finding of a listing that was folded becomes inactive without an alert and says which component it is watched as; the finding kept gets no new revision. With an analysis model enabled, the findings of a system whose duplicates were folded are analysed again once, as after any change to that system's components, and a finding that waits for a review of an AI dismissal asks for that review again.
- **Opening the database could fail while another process closed it.** SQLite deletes the `-wal` and `-shm` files when the last connection closes; on macOS another process can still find such a file with no links left, and the check that refuses hard-linked database files took it for one ("Database paths must be regular files without symbolic or hard links"). A file being deleted now counts as gone. Seen as a failing CI job when three processes opened one database at once.

## 1.4.0

Security Watch answers now what the monitor answers over time, for people and for AI coding agents, and is published as a container image with signed build provenance. Existing configurations, inventories and databases work unchanged. To be published under the default `latest` tag; the GitHub Action is used as `uses: ShieldaAI/security-watch@v1.4.0`.

### Added

- **`security-watch check`.** One command, no configuration, nothing stored: reads a project's dependency files (or `--sbom FILE`), asks OSV about every package version, marks CISA known-exploited entries and, with `--epss`, adds EPSS. Findings are sorted malware first, then known exploited, then by priority, each with the fixed versions above the installed one and the files the package came from. `--base REF` reads the dependency files at a git commit with `git cat-file` (nothing is checked out, and a partial clone fetches nothing) and reports what the working tree added, what it fixed, and which packages were added, removed or changed. `--package ecosystem:name@version` (repeatable) checks packages before they are added; `--advisory ID` says whether a CVE, GHSA, PYSEC, RUSTSEC, GO or MAL record affects the project, following a CVE record's aliases to the records that name packages. `--base REF...` compares with the point where the branch left REF. Both sides are the files git knows (the working tree: tracked files and untracked ones that are not ignored), so submodules and ignored folders are left out. `--json`, `--production`, `--fail-on`. Exit code 1 when an installed version is affected at or above `--fail-on` (high; malware and known-exploited always count; an advisory without a severity counts as medium; a package without an exact version never fails), 2 when the check is incomplete: a source failed or a dependency file could not be read, which is said first in the output. A package with several findings gets one version that fixes them all. It runs the monitor's own engine on an in-memory database, so a check and the monitor agree. Library functions `checkProject`, `checkPackages`, `checkChange` and `checkAdvisory` in `dist/check.js` (not yet part of the stable exports).
- **MCP server for AI agents.** `security-watch mcp [PROJECT]` and the `security-watch-mcp` bin serve seven tools over stdio: `check_project_vulnerabilities`, `check_dependency_change`, `check_package`, `check_advisory`, `list_dependencies`, `write_sbom` (the only tool that writes: inside the project, never replacing a file unasked) and `list_watch_findings` (read-only, listed only when `SECURITY_WATCH_CONFIG` names a monitor configuration). Paths must stay inside the project, links that lead out are refused, and a server started in a filesystem root or the home folder asks the client for its roots (a tool call waits for the answer). A cancelled call stops before its next request to a source and sends no reply. `write_sbom` writes only outside hidden folders, never through a link that leads out, and replaces only an existing SBOM, with `overwrite: true`. Protocol versions 2024-11-05 to 2025-11-25. See [Security Watch for AI agents](docs/agents.md).
- **Plugin for Claude Code, Codex, ChatGPT and Antigravity.** `plugins/security-watch`: the MCP server through a launcher that runs npm's own npx for the pinned version from outside the project (so the project's `.npmrc` and `node_modules` cannot choose the checker), and two skills, one for checking dependencies before and after a change and one for setting up the monitor. Marketplace `shielda-security-watch` (`/plugin marketplace add ShieldaAI/security-watch`). `npm run pack:plugins` builds the archives for OpenAI's portal.
- **Container image.** Every release tag publishes `ghcr.io/shieldaai/security-watch` (`x.y.z`, `x.y` and `latest` for stable releases) for linux/amd64 and linux/arm64, after the test suite and the container checks pass on each architecture's own hardware, with an SBOM and build provenance attached and a GitHub build provenance attestation signed through Sigstore (`gh attestation verify`). It uses only GitHub's own actions. `compose.yaml` uses it. The image carries the OCI source label and the MCP Registry label.
- **MCP Registry entry.** `server.json` lists the npm package and the image as `io.github.ShieldaAI/security-watch`; `package.json` carries the matching `mcpName`.

### Changed

- The published package includes `npm-shrinkwrap.json`, written from `package-lock.json` at pack time with runtime packages only, so `npx` and global installs get exactly the dependency tree the release was tested with, sub-dependencies included. `npm run check:package` installs the packed tarball and checks every runtime package version.
- `compose.yaml` pulls the published image instead of building one.

### Fixed

- The README no longer lists EPSS among the integrations Security Watch lacks; it has had EPSS since 1.2.0.

## 1.3.0

Security Watch hands findings to whoever writes temporary mitigations (runtime shields, blocking policies, firewall rules), shows which hosts a mitigation covers, works with [Shirudo](docs/shirudo.md), writes OpenVEX for other scanners, and reads CycloneDX up to 1.7. Existing configurations and inventories work unchanged. To be published under the default `latest` tag; the GitHub Action is used as `uses: ShieldaAI/security-watch@v1.3.0`.

### Added

- **Fix links, fix commits, weaknesses and exploit code are kept.** OSV and GitHub advisories keep their typed links: code changes (commits, pull and merge requests, compare views of two releases, patches, kernel.org, gitweb, googlesource and Mercurial commits) are `fix`; a page typed as a fix that is not a code change, and any change to an advisory database, is an `advisory`. OSV keeps the commits its `GIT` ranges name as fixes, both keep their CWE identifiers, and cve.now keeps its Exploit-DB, Metasploit, Nuclei and GitHub proof-of-concept entries when they name something. Only https links to public names, without credentials or inner whitespace, at most 40 links, 20 commits and 20 weaknesses per advisory. A malformed value is dropped, never the advisory. They are never sent to models and are left out of an advisory's content hash and a finding's analysis basis, so the upgrade records no new evidence revision, re-sends nothing and asks no model again. `explain` shows them. New `Evidence` fields `references`, `fix_commits`, `weaknesses` and `exploit_sources`; exported types `AdvisoryReference`, `FixCommit` and `ReferenceType`.
- **`security-watch shield-candidates`.** Lists active findings that are critical or known or reported to be exploited (`--all` for every finding that may affect you), with a `readiness`: `fix_known` (the installed version is affected and an advisory links the fix for this package), `fixed_version_known`, `advisory_only` or `news_only`, and a `missing` list in plain words. News alone is never enough to write a mitigation, and is listed as such. An advisory that covers several packages counts its fix links only for the package they name. `--unmitigated` leaves out findings that every source proves mitigated on every host now; `--omit-location` leaves out system IDs, names, owners, notes, package URL qualifiers, news links and mitigation details; `--output NEW.json` writes a new private file. Read-only. Library function `shieldCandidates` and its types.
- **Mitigation status, optional.** A `mitigations` list (up to ten sources) reads JSON Lines files that your tools write on a timer, in Shirudo's `node_vulns` format or a [generic format](docs/mitigations.md#mitigation-status) any tool can write (with an optional `expires_at`), and shows per finding how many hosts of the system are mitigated, waiting, failed, excluded, withdrawn, expired or not mitigated, and what is in place: in alerts, digests, `explain`, `findings`, `shield-candidates` and `vex` (`Assessment.mitigations`, exported types `MitigationStatus`, `MitigationState`, `MitigationSource` and `MitigationFormat`). Like EPSS it is shown only: it changes no applicability, priority or routing, creates no revision and never closes a finding. A missing, unreadable, empty, out-of-date or future-dated file, values the release does not know, and rows that all miss the inventory are monitoring-health errors; `doctor` checks every file. A saved status is judged again when read, so `findings`, `explain`, `shield-candidates` and `vex` never show it as current after scans stop or a mitigation expires. Security Watch never connects to a mitigation tool.
- **`security-watch shirudo-sboms`.** Copies the SBOMs of Shirudo's images from a local copy of its SBOM store into the SBOM folder, one system per image (the image ID, stable across upgrades). With the export it watches the images machines run, merging the SBOMs of versions that run side by side; without it, the newest version. It writes, replaces and removes only its own files, compactly and atomically; it removes a file only when its image is known to be gone, never because a read failed, the store is empty or the export is incomplete, and removes more than half of its images only with `--allow-removals`; it reports an image whose ID another system uses (with `--config`, also systems described by hand); and it shows its plan unless `--apply` is given. Library function `syncShirudoSboms`.
- **`security-watch vex`.** Writes an OpenVEX 0.2.0 document for library findings with an exact package version: `affected` with the action (update, follow the advisory, remove a malicious package, and a current mitigation), `under_investigation`, and `not_affected` only with `--include-not-affected`. Package URLs come from the inventory with only descriptive qualifiers (`classifier`, `type`, `arch`, `distro`, `os`, `epoch`), or are built per the package URL specification. Statements of the same package in several systems are merged to the most severe. An unchanged state gives the same document identifier. `--omit-mitigations` leaves the mitigation part of the action out. Library function `openVex`.
- **CycloneDX 1.2 to 1.7.** SBOMs from CycloneDX 1.2 up to 1.7 are read (1.4 to 1.6 before); a later 1.x is read by the 1.7 rules with a notice that does not degrade monitoring; 2.x and malformed versions are refused. A CycloneDX document without a `components` list is an empty system instead of an error. `security-watch sbom` still writes 1.6, which more tools read.
- Guides: [temporary mitigations](docs/mitigations.md) and [Security Watch with Shirudo](docs/shirudo.md).

### Verified

- The VEX output was loaded into Trivy 0.71.2 (`trivy sbom --vex`): `not_affected` statements suppressed exactly their CVEs for npm (including a scoped package whose inventory purl was written with a literal `@`) and for a Maven package whose purl Security Watch built; `affected` and `under_investigation` statements left the findings in the report.

### Not verified

- The Shirudo integration follows Shirudo's documentation of 24 November 2026 and is tested against files in that format, not against a running Shirudo deployment, which needs Shirudo's kernel patches and a TPM. Shirudo is pre-release.
- Upgrading is tested with a database written by the released 1.2.1 build (`test/fixtures/watch-1.2.1.db`): no revision, fingerprint, delivery or analysis basis changes.
- How often advisories carry fix links and exploit entries was measured on one advisory (Log4Shell), not on a corpus.

## 1.2.1

Fixes from an edge-case review: alerts sent twice for analysed news, packages missed in Python and Go projects, and a worker that paused when the clock stepped back. No configuration change. To be published under the default `latest` tag; the GitHub Action is used as `uses: ShieldaAI/security-watch@v1.2.1`.

### Fixed

- **Alerts sent again for analysed news.** With models on, a news finding the model had confirmed was sent again after any change to its analysis basis, such as one unrelated package added to the system: the scan saved it without its analysis first, and the same conclusion after analysis was a new revision. A known-exploited or critical one was sent twice more. Its queued alerts are now held until the analysis is redone and sent only if the conclusion changes or was not yet delivered; routing that does not depend on the model (an override, a source severity) still applies at once.
- **A shorter suppression now releases the alert.** `suppress --hours 720` followed by `suppress --hours 1` kept the queued alert waiting 30 days while `explain` said it was not suppressed.
- **Clock set back.** When the system clock stepped back (an NTP correction), the worker stopped scanning, writing its heartbeat, pinging the external monitor and running maintenance until the clock reached the old time again. Slack retry times and digest times are still wall-clock times.
- **`pyproject.toml` beside a requirements file.** A folder with `pyproject.toml` and only `requirements-dev.txt` lost the pyproject's packages, so their advisories were missed. A requirements file no longer hides the pyproject; it adds what the requirements files lack. A real lockfile still does.
- **go.mod `replace` with a version.** `replace golang.org/x/net v0.1.0 => golang.org/x/net v0.18.0` was applied to every version, so a required v0.17.0 was reported as the fixed v0.18.0. A replace that names a version now applies to that version only.
- **News naming a Python package by its published spelling** (`ruamel.yaml`, `typing_extensions`) now matches the package, which is kept in its normalised form (`ruamel-yaml`).
- Git and URL entries in an npm v1 lockfile, and Git, path and URL packages in `pdm.lock`, are no longer watched as registry packages of the same name.
- A Yarn Berry resolution with archive parameters (`lodash@npm:4.17.20::__archiveUrl=…`) keeps its version.
- An inventory `lockfile:` that starts with a byte order mark is read instead of failing the inventory.

## 1.2.0

News that no advisory has scored yet gets a level from what the articles say, and findings can show EPSS. Existing configurations and inventories work unchanged. To be published under the default `latest` tag; the GitHub Action is used as `uses: ShieldaAI/security-watch@v1.2.0`.

### Added

- **News signals.** For a news finding with no advisory severity (a zero-day without a CVE, a CVE that is reserved but not published, a vendor bulletin), the articles are read, without a model, for a CVSS score, a vendor's word rating, a report of exploitation, a denial of exploitation and public exploit code. A score or rating raises the finding's priority to at least its level; a report of exploitation raises it to critical, so with `urgent_unknown` (the default) the finding is sent at once as possibly critical. A statement counts only when it is tied to the finding's subject (its CVE or GHSA identifier, or the product or package it matched); negated and hedged statements and "zero-day" alone are not reports. Signals never lower, dismiss or mark a finding as known exploited, and stop being read once an advisory with a severity joins the finding. Alerts and digests have a `News signals:` line with the score, rating and subject only; `explain` shows the sentences they were read from. See [news signals](docs/configuration.md#news-signals).
- `policy.news_signals` (default `true`) turns news signals off.
- **EPSS, optional.** `sources.epss: true` looks up FIRST's EPSS for the CVEs of each current finding (including the CVE aliases of a GHSA-keyed library finding) and shows the highest, with its CVE, in alerts, digests, `explain`, `findings` and the scan report (`Assessment.epss`, exported type `EpssScore`). Only CVE identifiers are sent to `api.first.org`, in batches of 50, at most ten requests a scan, each score refreshed once a day. It is shown only: it changes no priority or decision, and a new daily score creates no finding revision, reopens no review and asks no model for a new analysis. A failed lookup is a notice, and findings keep the last score. See [EPSS](docs/configuration.md#epss).
- `Assessment.news_signals` and the exported types `NewsSignals` and `NewsStatement`.
- The configuration guide lists feeds that carry full articles with scores or exploitation reports (Rapid7, Tenable, The Register, Security Affairs, the Zero Day Initiative) and those that carry only headlines.

### Changed

- **Louder for unscored news.** A news finding that an article reports as exploited, or that an article scores at 9.0 or above, now alerts at once where 1.1 put it in the digest. Measured on one week of real articles against a 20-product inventory: five findings were raised and one more immediate alert was sent (an actively exploited ScreenConnect plugin). The first scan after the upgrade reassesses news findings still in the news window, so a raised one is sent once.

### Not verified

- Measured on 256 articles from one week of November 2026, labelled by the developer, not by an independent reviewer. The human-labelled pilot and a real Slack and email delivery remain open, as in 1.0.

## 1.1.1

Fixes for feeds that were read wrongly and for two checks that trusted a name. No configuration change. To be published under the default `latest` tag; the GitHub Action is used as `uses: ShieldaAI/security-watch@v1.1.1`.

### Fixed

- **Feeds with an image in `<media:content>` were read without their text.** The article in `<description>` was ignored whenever an item also had a `<media:content>` element, so every item from feeds such as Rapid7's blog and Dark Reading arrived with an empty description and could match only by its title. The first of `content:encoded`, `content`, `description` and `summary` that holds text is now used. An empty `content:encoded` also falls through to the description.
- **Feeds that escape their HTML with entities showed the tags as text.** A description written as `&lt;p&gt;` (Tenable's blog, the seclists.org lists) arrived as the literal text `<p>`, `<br>` and similar, which reached matching, models and alerts. A field that carries HTML (RSS `description` and `content:encoded`, Atom `content` and `summary` with `type="html"`) and holds no raw `<`, which escaped XML text never does, is now unescaped once as XML (the five predefined entities and character references only; DTDs are still refused) before it is read as HTML. CDATA and plain-text fields (titles, Atom text content) are read as before, so `&lt;script&gt;` in a title stays text. The first scan after the upgrade records a new revision of items from such feeds that are still in the news window.
- **A name that starts like a loopback address no longer counts as one.** `intake.listen: 127.example.com:8787` was accepted without TLS or `allow_plain_http`, because the check read the text of the host. Only `localhost`, an IPv4 address in 127.0.0.0/8 and the IPv6 loopback address count now.
- **`sbom --project FILE` refuses a symbolic link.** A link named like a dependency file was followed to whatever it pointed at, unlike files found inside a project folder, which were already skipped. A project folder given as a link is still read.

## 1.1.0

Start from your code instead of a hand-written inventory, and keep the inventory current from CI. Existing configurations and inventories work unchanged. To be published under the default `latest` tag. The GitHub Action is used as `uses: ShieldaAI/security-watch@v1.1.0`.

### Added

- **`security-watch sbom`** reads the lockfiles and manifests in a project and writes a CycloneDX 1.6 SBOM: npm (`package-lock.json` v1 to v3, `yarn.lock` 1 and 2+, `pnpm-lock.yaml` 5 to 9, `package.json`), Python (`poetry.lock`, `uv.lock`, `Pipfile.lock`, `pdm.lock`, `requirements*.txt`, `pyproject.toml`), Go (`go.mod`), Rust (`Cargo.lock`), PHP (`composer.lock`, `composer.json`), Ruby (`Gemfile.lock`, `Gemfile`), Java (`pom.xml`, `gradle.lockfile`), .NET (`packages.lock.json`, project files, `Directory.Packages.props`), Dart, Elixir, Swift and Haskell. It reads files only: no package manager, no symbolic links, no network. Each package records the files it was found in, and alerts show them (`Affected item: npm express 4.21.2 - found in package-lock.json`). `--owner`, `--note`, `--environment`, `--exposure`, `--criticality` and `--system-id` describe the system; in GitHub Actions and GitLab CI the repository address and commit are filled in. `--production` leaves out development-only dependencies. The command exits 1 when it finds no packages.
- **`init --project PATH`** creates a monitor for one or more projects in one step: an SBOM per project in `sboms/`, an inventory that reads that folder, and OSV turned on when a project has packages outside npm.
- **SBOM folder.** `sbom_directory` in the inventory makes every `.json` SBOM in a folder a system, read again at every scan. The SBOM's creation time is the system's `updated_at`, so an SBOM that stops arriving is reported as stale. A file that cannot be imported is reported and left out without stopping the other systems. Operating-system packages in container SBOMs (deb, rpm, apk and similar) are listed once as a notice instead of degrading every scan.
- **SPDX import.** `import-sbom`, the system `sbom` field and the SBOM folder accept SPDX JSON 2.2 and 2.3, including GitHub's dependency-graph export, as well as CycloneDX. SBOMs from Trivy, Syft and cdxgen are accepted as they are.
- **SBOM receiver.** An `intake` section makes `start` accept `PUT /v1/sboms/SYSTEM_ID` from pipelines, with bearer tokens limited to system IDs (lower case, as `sbom` writes them), TLS (or plain HTTP on loopback, or behind a TLS proxy with `allow_plain_http`), a 20 MiB limit, a slowdown after repeated failed tokens, and an answer a pipeline can act on: the upload is imported before it is written, so an unusable SBOM fails the job at once. `security-watch intake` runs the receiver alone. `security-watch upload` and `sbom --upload URL` send an SBOM, retrying network errors and busy answers; the GitHub Action takes `upload-url` and `upload-token`. An empty SBOM folder is accepted, so a monitor can start before the first upload.
- **GitHub Action** (`action.yml`): `uses: ShieldaAI/security-watch@v1.1.0` writes the SBOM and uploads it as an artifact, or checks and uploads an SBOM made by another tool (`sbom-file`).
- [Watch a project from its dependency files](docs/sbom.md): supported files, CI recipes, ways to deliver SBOMs to the monitor, and other generators.
- Library exports: `generateSbom`, `importSbom`, `DEPENDENCY_FILES`, `startIntake`, `createIntakeHandler`, `uploadSbom`, and the types `SbomOptions`, `GeneratedSbom`, `DependencyFile`, `IntakeUpload`, `IntakeOptions`, `RunningIntake` and `UploadOptions`. `SbomImport.source.format` may be `SPDX`, and `SbomImport.subject` describes the system an SBOM is about.

### Changed

- CycloneDX components with `evidence.occurrences` take the listed locations as their note.
- The inventory's `systems` list may be empty when `sbom_directory` is set; an inventory with no system at all is still refused.
- The README starts from `init --project`; the npm description and keywords say that lockfiles and SBOMs are read.

## 1.0.0

First stable release, published to npm on 2026-11-15 under the default `latest` tag from commit 43db188.

### Upgrading from 0.1.0-alpha.0

1. Use Node.js 24.10.0 or newer (the alpha accepted 24.0).
2. Stop the old worker and take a backup: `security-watch backup --output PATH`.
3. Install the new version, then run `security-watch scan` or `security-watch start` once. This migrates the database to schema 7. Read-only commands refuse to run until that has happened. There is no downgrade path other than restoring the backup with the old version. Findings that did not change keep their revision, their delivered alerts and their acknowledgements: the upgrade does not send them again.
4. Run `security-watch doctor`. It now reports an SMTP address it cannot use, a verification model identical to the analysis model, and inventory entries that were left out (`import_warnings`) and npm names that may be a typing mistake (`name_notices`). It exits with status 2 whenever it prints `ok: false`.

Behaviour that changes for an existing installation:

- **AI dismissals are reviewed by default.** News that a model classifies as general news or as not affecting you goes to a local review queue and the digest instead of being recorded silently. Set `policy.ai_dismissals: record` to keep the old behaviour.
- **Models receive less.** Each model defaults to the `minimal` disclosure profile: package and product names and versions only.
- **`models.verification` must differ from `models.analysis`.** A pair that reaches the same model at the same address is rejected at start-up, however each one is written (a spelled-out default endpoint, a trailing slash, different letter case, a compatible-endpoint profile pointing at the same service).
- **`models.daily_token_limit` defaults to 1,000,000** (was 100,000), and a request now reserves one token per three bytes instead of one per byte. The old defaults allowed about four requests a day.
- **Plain `http://` endpoints** (models and the external heartbeat) are accepted only for local or private hosts, even with `allow_private_endpoint: true`. An address is judged by its range; addresses that wrap a public IPv4 address (NAT64, 6to4) count as public for this rule, and HTTPS requests to them are refused. A name is accepted when it has no public form (`ollama`, `ollama.ml-tools`, `*.internal`, `*.ts.net`, `*.test`, `*.home` and similar), and the request is refused if the name resolves to a public address.
- **Inventory text is one line.** System `id`, `name`, `owner`, `environment`, keywords, product names and every `note` are rejected when they contain a control character (tabs and line breaks included) or a Unicode line separator. These values are printed in notifications.
- **News is matched to packages by stricter rules.** A package whose name is an English word (`express`, `moment`, `request`) no longer matches a story by the word alone; it needs to be named as a package ("the request package", "npm install send", "the npm package next"), a release, or to be written as a name. An existing news finding that rested on such a word becomes inactive at the first scan after the upgrade. Advisories, which are matched by structured package claims, are not affected. The word "module" no longer counts as package context.
- **A capitalised package name typed by hand is pointed out** (npm, RubyGems, Hex, Pub). `npm:Lodash` is accepted, because some packages from before 2017 keep their capitals (`MD5`, `CSSselect`), but it matches only advisories for exactly that spelling. `doctor` lists such entries under `name_notices` and every scan report carries them in `notices`. A notice is not a fault: the scan is not degraded, no health alert is sent, and the heartbeat is not withheld. Names imported from a lockfile or SBOM, and `JSONStream`, `Base64`, `JSONPath` and `JSONSelect`, are taken as published.
- **cve.now reads one week past its checkpoint** on every scan (about 45 listing requests at the current rate of some 600 records a day, under a minute) to find records the service ingested after their publication date.
- **The first cve.now scan looks back one day** (was seven). A week meant about 4,500 detail requests and 80 to 90 minutes before the first result. Exact npm package matches still cover all of history.
- **Recipient domains are compared in lower case.** Email to `Ops@Example.ORG` was delivered but recorded as uncertain.

### Added

- **Notes that say where to look.** Systems, libraries and products accept a `note`; library list lines accept `# note`. A notification about a system carries a `Where to look:` line with the system name, owner and notes, and one about a library or product also an `Affected item:` line. ### Fixed: delivery, storage and import

- An SMTP address with an unencoded `%` was recorded as an uncertain receipt. Failures that provably happen before the message is handed over (connection, TLS, greeting, a dropped session before `MAIL FROM`) are retried instead of being marked uncertain. A rejected sign-in (response code 535) is a configuration fault and fails at once; a temporary refusal (4xx) is retried. Once `MAIL FROM` has been written, a dropped connection or timeout is recorded as uncertain and never retried automatically.
- Text from an advisory (title, fixed version), a model or the inventory could contain a line break and so add forged `Rule:`, `Finding:` or `Where to look:` lines to a notification. Every value is now placed on one line.
- `backup --output` left a file at the destination when verification failed.
- Two processes opening an old database at the same moment could leave it unopenable.
- A job superseded while it was being sent stayed `pending` after a failed attempt.
- A send displaced by a second database handle stopped the worker.
- A legacy npm name (`JSONStream`) or one unreadable lockfile or SBOM entry rejected the whole inventory; CycloneDX documents without `dependsOn`, with an unencoded npm scope, with `v`-prefixed Go versions, with an empty `version`, with an upper-case package type (`pkg:NPM/…`), or with a Python version written two equal ways (`1.0` and `1.0.0`) were rejected. A component with an unreadable package URL or a non-text version is left out with a warning. Two genuinely different versions for one component, duplicate references and malformed hashes still reject the document.
- A version citation that only matched a digit inside another number (`4` inside `4.2` or a CVE number) satisfied model validation; news evidence without a content status was treated as a fully read article.
- `doctor` printed feed addresses after variable substitution, and exited with status 0 while reporting an unusable SMTP address.
- With `models` left out of the configuration, `daily_token_limit` defaulted to 100,000 instead of the documented 1,000,000.
- A setup without an AI model reported every scan as degraded: exit code 2, a standing health finding and alert, and withheld external heartbeat pings. "AI is disabled" is now a `notices` entry in the scan report.

### Changed

- The published `Store` type no longer declares the worker's internal methods (`claimDue`, `completeJob`, `recoverSending`, `setMeta`, `reserveBudget` and others). They still exist at run time and are not part of the public API. `ModelAnalyzer` accepts the published `Store`, or a caller's own state described by the exported type `ModelState`.
- A replacement `emailSender` can no longer signal "nothing was sent" through an error's `code` or `command`: such labels do not prove it. Its failures are retried only on an SMTP 4xx response code, recorded as failed on a 5xx code, and otherwise recorded as uncertain.
- Publishing goes through `npm run release`, which chooses the tag from the version, accepts only `--dry-run` and `--otp=CODE`, and refuses to start when npm is set to ignore scripts or to use another registry. A bare `npm publish` is refused, because `npm publish --tag latest` cannot be told apart from it inside a lifecycle script. The release check also refuses a package that would contain a file that is not in git. These checks guard against mistakes; `npm publish --ignore-scripts` skips them, as it skips every lifecycle script.
- Types are exported by name instead of `export *`.
- Dependency: `fast-xml-parser` 5.12.1 (GHSA-474x-hrwr-fgx4).
