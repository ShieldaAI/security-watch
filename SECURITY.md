# Security policy and boundaries

Security Watch is a monitoring tool without an independent security audit. Security reports are handled on a best-effort basis by a single maintainer, with no guaranteed response time; fixes are released for the latest 1.x version. Validate findings against your deployment before using them to make remediation decisions.

## Report a vulnerability

Use [GitHub's private vulnerability reporting form](https://github.com/ShieldaAI/security-watch/security/advisories/new). If that option is unavailable, ask a maintainer for a private reporting channel without posting exploit details, credentials, private inventory or affected customer data publicly. Do not send real secrets in examples. There is no dedicated security reporting address yet.

Include the relevant commit/version, Node version, a minimal synthetic reproduction, expected versus observed behavior, and which trust boundary is crossed. Reports involving lost alerts, false safety conclusions, credential disclosure, unsafe network access or duplicate/incorrect delivery are particularly useful.

## Trust model

Trusted inputs are the operator's configuration, inventory, chosen model/SMTP endpoints, environment, local filesystem and installed application/dependencies. Feed bodies, article text, advisory text and model output are untrusted evidence. The application does not protect against a malicious local administrator, compromised dependency, hostile model endpoint explicitly trusted by the operator, or altered system clock.

Implemented boundaries include:

- Strict configuration/inventory parsing, bounded input sizes and metadata-only lockfile and SBOM import. `security-watch sbom` reads dependency files as text: it runs no package manager or build tool, follows no symbolic link and makes no network request, so it is safe on an untrusted checkout. No package installation or lifecycle-script execution occurs during monitoring.
- The optional SBOM receiver (`intake`) is the only listening socket and is off by default. It listens on loopback unless configured otherwise, refuses to listen beyond loopback without TLS unless `allow_plain_http` is set for use behind a TLS proxy, requires a bearer token of at least 32 characters compared in constant time, limits each token to configured system IDs, slows repeated failures from one address (without refusing a valid token, so bad tokens sent through a shared proxy cannot lock a pipeline out), bounds bodies to 20 MiB and concurrent uploads to four, and writes an upload only after it imports, atomically, under a name built from a validated system ID. An upload cannot change hand-written systems, configuration or other files; it can set the owner and note that alerts show for the systems its token allows. Uploaded SBOMs are untrusted input to the same bounded importer as local ones.
- Public HTTPS fetching with checks on the addresses used by the connection, bounded redirects/timeouts/response sizes, and removal of authentication headers on cross-origin redirects. Model and external-heartbeat endpoints may explicitly opt into private addressing; plain HTTP is then allowed only to private or local addresses, checked again on the addresses the connection uses. SMTP endpoints are operator-selected.
- Models receive no shell, browser, filesystem or notification tools. Output is schema-checked, evidence IDs must exist, and supporting quotes must appear in the supplied evidence.
- The Hacker News article requests are restricted to its publication hosts and have size limits. Article links to other sites are not crawled. Missing, excerpted, stale or truncated evidence cannot support a new decisive AI impact conclusion. Historical general-news classifications are retained; current affected/excluded claims require fresh evidence.
- Deterministic package matching and source-severity floors govern library/product decisions. AI cannot rewrite recipients, authoritative version constraints or dependency applicability.
- AI news classification and claimed system impact are stored separately from authoritative applicability. Evidence-backed general news or an AI-reported exclusion can suppress noncritical news alerts, but cannot override source-critical or enabled known-exploitation safeguards.
- Slack destinations come only from operator configuration and are restricted to standard `hooks.slack.com` incoming webhooks. SMTP requires TLS. Notification content is rendered as text and cannot enable attachments, filesystem reads or URL-fetching features in the email transport. Each value from an advisory, a model or the inventory is placed on a single line behind that line's own label, with runs of blank characters reduced to one space, so it cannot add a line that looks like one of the message's own labels; inventory text fields reject control characters and line separators when the inventory is loaded.
- Findings and their delivery jobs are committed together. Ambiguous delivery is visible and requires a manual receipt check before retrying. An email is retried automatically only when the failure provably came before the message was handed over (before `MAIL FROM`) or the server refused it with a temporary response code; a connection lost after that point is recorded as uncertain.

Models can misinterpret sources, feeds can omit important facts, and advisories can be wrong or delayed. Check source failures and uncertain findings during operational review. The bot does not provide a general prompt-injection detector or execution sandbox.

## Data handling

cve.now stack requests reveal deduplicated npm package names and exact versions through URL query parameters; lockfiles and system/deployment metadata are not uploaded. The Hacker News feed and article servers receive normal HTTP request metadata. Optional OSV requests reveal library ecosystem, package name and the installed version when supplied. Official vendor feeds receive normal request metadata. With `sources.epss`, `api.first.org` receives the CVE identifiers of current findings, which together suggest which software you run. Other enabled advisory/feed servers receive normal request metadata, and GitHub may receive the configured API token.

Each configured AI model defaults to the `minimal` disclosure profile. It receives selected relevant package ecosystem/name/version and product name/version, request-local IDs and inventory freshness status, plus target event and selected evidence fields/excerpts. Original inventory IDs, system name/owner, repository URLs, provenance, dependency graphs, verification declarations, remediation records and operator identities are excluded. `deployment-context` opts that specific model into environment/exposure/criticality and evidence-matching keywords, never other inventory metadata. The verifier applies its own profile independently. Allowed names and evidence text are not secret-redacted; do not place private content there unless the endpoint is approved to receive it. Full contracts and migration behavior are in [model disclosure configuration](docs/configuration.md#data-sent-to-models).

Inventory notes (the `note` field on systems, libraries and products) are the operator's own pointers to where something runs. They are stored in the local database and shown in notifications together with the system name and owner. They are never sent to advisory sources and are excluded from model requests under both disclosure profiles. Do not put secrets in a note.

`shield-candidates` prints system IDs and the same inventory names, owners and notes, plus package names, versions and advisory links, as local JSON. `--omit-location` leaves out system IDs (often a system's name), names, owners, notes, package URL qualifiers (which can name a private registry) and links to news articles (a feed can be internal); use it before giving the list to an agent or service outside your network. Identifiers, package names and versions stay, because a mitigation is written from them. `vex` writes package URLs from your inventory with only descriptive qualifiers (`classifier`, `type`, `arch`, `distro`, `os`, `epoch`), and its action statements can name your mitigation tool and host counts unless `--omit-mitigations` is given; read a document before you publish it. Mitigation status files are local files that Security Watch only reads; it connects to no Shirudo, ClickHouse or other mitigation service and holds no credential for one. `shirudo-sboms` reads a local copy of Shirudo's SBOM store, follows no symbolic links, and writes, replaces and removes only the files it marked as its own in the SBOM folder.

Notifications disclose formatted finding context, the inventory names and notes above, and source links to Slack or the configured email recipients under separate routing policy; model disclosure settings do not filter notification payloads or public inventory queries. There is no automatic application telemetry. An optional, operator-configured heartbeat endpoint receives bodyless success pings and normal request metadata. It receives no inventory, finding content or logs.

Credential values are read from environment variables, not placed in model prompts or intentionally persisted in SQLite. Do not insert keys into model names, feed URLs, inventory text or configuration substitutions. Use your service manager or secret manager to supply credentials; the CLI does not automatically load `.env` files. Do not commit configuration, database files, backups or `.env` files to source control.

SQLite stores evidence, finding revisions, model analysis excerpts, caches, budgets and delivery state. Database files use private permissions but are not application-encrypted. Use appropriate host access controls and encrypted storage. Retention and scheduled backups are disabled until configured. Cleanup preserves active or unresolved findings, unresolved delivery audit, source checkpoints and budgets; it is bounded and has a read-only preview. Scheduled backup rotation removes only managed snapshots after a new snapshot verifies successfully. Backups can contain the same sensitive material as the live database. Verification copies a standalone snapshot into a private temporary directory and checks structural restoration, including migrations, without replacing live state. This is not validation of every stored security claim; plan disk capacity and protect backup destinations.

## Coverage limitations

- Library inventory supports 12 ecosystems. npm names are matched exactly, including letter case: a capitalised name typed by hand is listed as a notice by `doctor` and in every scan report, because it matches only advisories published under that spelling; the notice does not degrade monitoring. npm and a bounded PyPI final-release subset use supported version-range evaluation and exclusions; complex PEP 440 forms remain unknown. Other ecosystems require a positive exact OSV query or an explicitly listed affected version; a missing version, unmatched result or unsupported range stays unknown. Lockfile entries include dependencies that may not be present in production.
- Generic products, operating systems and SaaS services have name/keyword candidate matching plus optional AI news/impact analysis. AI impact is an evidence-backed opinion, not a deterministic product-version result. Vendor backports, enabled features and exploit reachability are not automatically established.
- Missing versions, unknown constraints and stale inventory remain uncertain. An empty advisory search does not establish that a system has no vulnerabilities.
- CVSS v3.0/v3.1 calculation and supplied source labels/scores are supported. For OSV and GitHub records, CVSS v4 base vectors are scored with the pinned FIRST reference calculator; threat and environmental metrics are not applied, and unsupported vectors are counted and left unknown. See [CVSS v4 support](docs/cvss-v4-support.md).
- A package named only in the prose of a news story is matched by rules, not by understanding: a name that is an English word must be named as a package, carry a release or be written as a name, a scoped package is matched by its full name only, and a Maven library by its coordinates or by an artifact name that is not an English word. Stories about such packages can be missed and, less often, an unrelated story can match; see the [matching rules](docs/configuration.md#sources-and-coverage). Advisories are matched by structured package claims and are not affected.
- News signals (stated CVSS scores, vendor ratings and exploitation reports read from articles for findings without an advisory severity) are text matching, not verification. An article can be wrong, out of date or written to mislead, and every feed you add is trusted to say what it means: a feed that falsely reports exploitation of a product you list raises that finding to critical and, with `urgent_unknown`, sends it at once. Signals only raise priority; they never lower, dismiss or mark a finding as known exploited, and statements that cannot be tied to the finding's subject in their sentence or clause are not read. A feed can still raise every product it names in a report of exploitation, one clause at a time; add only feeds you trust. See [news signals](docs/configuration.md#news-signals).
- Mitigation status is the operator's file, read as written: Security Watch does not verify that a shield, policy or rule is loaded, signed or effective. It is shown only and never lowers a priority or closes a finding. `shield-candidates` readiness describes the information the advisories provide, not whether a mitigation is possible or safe, and fix links and exploit entries are only as complete as the advisories. `vex --include-not-affected` makes claims that other scanners act on by hiding the vulnerability; they rest on published version ranges. See [temporary mitigations](docs/mitigations.md).
- Source requests and model inputs have size and request limits. Incomplete collection or analysis reports degraded monitoring and requires review.
- Recent cve.now entry collection, tracked/news-cited refreshes and exact npm stack queries do not establish exhaustive historical coverage for every product. The recent listing is read one week past the checkpoint; a record cve.now ingests more than a week after its publication date is found only through an exact npm match or a news citation. The Hacker News may block article access; the feed excerpt remains available for review without a confident impact conclusion.
- CycloneDX JSON 1.2–1.7 (later 1.x with a notice) and SPDX JSON 2.2/2.3 package metadata import, and SBOM generation from lockfiles and manifests (`security-watch sbom`), are supported, and OpenVEX output (`vex`), but not VEX ingestion, operating-system package matching, attestation verification or live deployment discovery. There is no authenticated web crawling, automatic remediation, distributed lock, multi-host worker or independent penetration-test certification.
- Notifications are not exactly-once delivery. A timeout can occur after a destination accepts a message. Verify receipt before retrying an `unknown` job.

Review `status`, `deliveries`, source-health findings and service logs. Optional external success pings stop when monitoring is unhealthy, but the receiving service must be configured to detect missing pings. Loss of the host or every delivery channel cannot be reported through that same failed infrastructure.

Inventory origin, digest, provenance, observation and configuration fields are operator declarations. They do not authenticate artifact origin or establish a deployed fix. Baselines are stored locally for drift comparison; do not include secrets. Coverage receipts describe bounded collection and must not be interpreted as an exhaustive vulnerability scan. Configuration-dependent remediation guidance remains subject to operator verification.

## Local AI dismissal review

Both AI-only quiet routes require review by default. `policy.ai_dismissals: record` explicitly opts out. Review and notification delivery are separate: sending a digest does not approve a dismissal, and no configured channel is required for the local queue. A human verdict binds the finding revision, reviewed source content and installed/model context. Source changes invalidate stale verdicts even before a scan completes reassessment.

CLI review commands rely on private local database/OS access. The reviewer string is an operator-declared audit label, not an identity-provider assertion. Review notes stay local and in backups. Generic retention protects review history and its evidence; review-specific expiry is not implemented. A local dismissal can cancel pending delivery but cannot recall an in-flight message. Review never changes authoritative version applicability.
